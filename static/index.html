Unified Multi-RAG Pipeline

Commands: Type your query to get an answer /ingest - Re-run structure-aware ingestion /scrape <URL> - Scrape PDFs from a URL /plan <query> - Show query plan before answering /compare <query> - Compare Knowledge Graph vs BM25 vs Semantic Search q, quit, exit - Exit

How it works

1. Data Ingestion

  • Files are read from data/: .pdf via pdfplumber, .docx via python-docx, .eml via Python's email module.
  • Text is split into overlapping chunks (750 characters, 200 overlap) with LangChain's RecursiveCharacterTextSplitter.
  • Each chunk is run through spaCy (en_core_web_sm) named-entity recognition, ignoring low-value types like dates, percentages and cardinal numbers.
  • A regex heuristic ("X is a / are / refers to Y") extracts simple IS_A relationships between capitalized phrases - a lightweight pattern match, not an LLM extractor.

2. Data Storage

  • Entities and relationships live in an in-memory SQLite database, snapshotted to data/corpus_analytics.json so they survive a restart.
  • Chunk embeddings are stored in a FAISS IndexFlatL2 index on disk (faiss_index/index.faiss), with the raw chunk text and source filenames pickled alongside (chunks.pkl).
  • BM25's tokenized corpus is kept purely in memory and rebuilt from those same chunks each time the app starts (or after a reindex).

3. Semantic Search

  • The query is embedded with sentence-transformers/all-MiniLM-L6-v2 (CPU) and matched against the FAISS index by nearest L2 distance.
  • Candidates from all retrieval sources are then re-ranked together by a shared local cross-encoder for the final ordering.

4. BM25

  • Classic lexical term-frequency scoring (rank_bm25.BM25Okapi) over lowercased, tokenized chunks.
  • Purely keyword-based - it complements semantic search by catching exact-term matches that embeddings can sometimes miss.

5. Dynamic Knowledge Graph

  • Not a separate graph database - it's a thin query layer over the same SQLite relationships table populated during ingestion.
  • Given an entity from the query, it does a 1-hop neighborhood lookup (rows where that entity is the source or target).
  • Powers aggregation-style questions and the "Knowledge Graph" column in /compare.

6. Agentic Retrieval

  • Triggered when the LLM query planner classifies a question as needing multi-hop reasoning.
  • Runs hybrid retrieval in a loop (up to a configured number of steps), accumulating and de-duplicating context.
  • Between steps, an LLM gap-assessment call decides whether the context gathered so far is sufficient or whether a follow-up query is needed.

7. Validators

  • Retrieval Validator - embedding cosine similarity between the query and each retrieved chunk (semantic relevance, not keyword overlap).
  • Groundedness Validator - splits the answer into sentences and checks each one's embedding similarity against the retrieved context, optionally blended with an LLM judgment.
  • Consensus Validator - pairwise cosine similarity between the Knowledge Graph, BM25, and Vector answers; low agreement flags a possible outlier.
  • These combine into a weighted final score that picks the /compare winner.
